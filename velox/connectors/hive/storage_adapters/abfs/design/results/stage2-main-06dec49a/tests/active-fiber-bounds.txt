Functional proof
The test selects one endpoint key for each process-local runtime shard, blocks
one admitted request on every shard, waits until all three fibers have started,
then submits two inactive requests and one overload request. The snapshot shows
exactly three active requests and two queued requests. The overload future is
ready and fails. Releasing all active requests executes both queued requests.

The runtime reports configured stack capacity separately from observed stack
use. Configured peak capacity is peakActiveRequests * fiberStackBytes. Measured
high-water use comes from Folly recordStackEvery sampling and
FiberManager::stackHighWatermark(); it is not inferred from configuration.
Folly disables this measurement under ASAN, where the metric remains zero.

Focused output
STAGE2_BOUND_METRICS shards=3 peak_active=3 max_queued=2 fiber_stack_bytes=131072 estimated_peak_fiber_stack_bytes=393216 measured_fiber_stack_high_watermark_bytes=4944

The measured 4944-byte value is evidence from this Debug execution, not a
production sizing recommendation or a claim that all workloads use the same
stack depth. The configured 393216-byte value is capacity, not actual use.

Overflow proof
A configuration whose maxActiveRequests * fiberStackBytes cannot be represented
by size_t is rejected during runtime construction.
